# ADR 0004: Step 3 organisation, taxonomy, profiles and verification

- **Status:** Accepted
- **Date:** 2026-09-22
- **Context:** Step 3 adds the organisational structure (schools/departments), the shared research taxonomy, student and researcher profiles, faculty verification and fictional seed data, per `docs/architecture.md` and the Step 3 prompt in `lpu-roadmap-prompts.md`.

## Decisions

1. **Module layout follows the approved planned-module list.** `taxonomy`, `profiles` and `researchers` are new modules named in `docs/architecture.md` §3. Schools/departments went into the existing `admin` module rather than inventing an unlisted "org" module: organisational structure is administrative, admin-only, and sits naturally beside admin user management. `admin/router.py` exposes a second router (`org_router`) so `/admin/users/...` and `/admin/schools|departments` can share the `/admin` mount without one router's prefix constraining the other.
2. **Saving a researcher profile submits it for verification.** The approved endpoint list has no separate "submit" action, so without this nothing would ever enter `PENDING` and the verification queue could never fill. `UNVERIFIED`/`REJECTED` → `PENDING` on save (a rejection can therefore be addressed and resubmitted); an already-`VERIFIED` profile keeps its status, because editing a bio should not silently revoke verification.
3. **A coordinator acting outside their department scope gets `404`, not `403`.** Per `docs/architecture.md` §6's status-code rule, they must not learn the profile exists. `403` is reserved for "you may see it but not do this", which is the wrong signal here. The permission check (`profile:verify`) still runs first, so a student or unverified faculty gets `403` without any resource lookup.
4. **First real use of the coordinator-scope policy layer.** `researchers/policies.py` holds `assert_not_self_verification` and `assert_in_coordinator_scope` — the "resource policy" layer that Step 2 deliberately deferred because no scoped resource existed yet. `ADMIN` is unscoped by design; `RESEARCH_COORDINATOR` must have a `DEPARTMENT` scope matching the target's `department_id`, and a coordinator with no scope set sees an empty queue rather than everything.
5. **`coordinator_scope_id` is now validated at the application layer.** Step 2 shipped the column with no FK (it is polymorphic across department/school/university). Now that `departments` exists, `admin/service.py: update_user` rejects a `DEPARTMENT`-scoped id that doesn't name a real department (`422`). Still no DB-level FK: a single column cannot foreign-key to three different tables.
6. **`tag_aliases` uses two real nullable FKs plus a `CHECK`, not a polymorphic id.** `num_nonnulls(skill_id, research_area_id) = 1` gives database-enforced integrity, which is possible here (only two possible targets, both created in the same migration) and isn't possible for coordinator scope. Different shapes for genuinely different problems.
7. **Research areas are two levels deep, enforced in the service layer.** A parent that already has a parent is rejected (`422`). Expressing "max depth 2" as a DB constraint would need a trigger or a materialised path; the service check is simpler and the taxonomy is only written by coordinators/admins.
8. **Tag suggestions are a separate table, not draft taxonomy rows.** Anyone authenticated can `POST /tags/suggestions`; coordinators/admins approve (which creates the real skill/research area) or reject. This keeps the canonical taxonomy clean — an unreviewed suggestion can never be selected on a profile.
9. **One `GET/PUT /me/profile` endpoint pair, role-dispatched server-side.** A student profile and a researcher profile are genuinely different schemas, not optional fields of one schema. The response uses a union `response_model`; the `PUT` body is read from the request and validated against whichever schema matches `current_user.role`, since FastAPI can't declare a role-conditional body type on a single route. A `profile_type` discriminator field is included in responses so the client doesn't have to sniff fields. Trade-off: the OpenAPI schema for that request body is less precise than a normal typed route; matching the approved endpoint contract was judged more valuable.
10. **`users.onboarding_complete` is stored and recomputed, not derived per request.** `PUT /me/skills` and `PUT /me/research-areas` recompute it (≥3 of each). Nothing consumes it until Step 9's recommendations, but it is exposed on `GET /me` so the frontend can route users into onboarding. `users.UserRead` gained `department_id`, `coordinator_scope_*` and `onboarding_complete` for the same reason — the flag existed in the database but no API surfaced it, which would have made it unusable.
11. **`PUT /me/skills` and `/me/research-areas` replace the whole set.** Idempotent, and it matches the picker UI (the client always knows the full intended selection). No per-item add/remove endpoints.
12. **Seed data is synthetic, flagged, and idempotent.** `scripts/seed_demo_data.py` names people `Demo Faculty 07` at `demo.faculty07@example.com` — not invented realistic human names, which could be mistaken for real people. Every seeded user carries `is_demo`. Re-running matches on natural keys and inserts nothing. The password comes from `SEED_DEMO_PASSWORD` or a `getpass` prompt and is hashed once and reused across the 108 demo accounts (a deliberate demo-only shortcut: Argon2 is slow by design, and no real account is involved).
13. **A few seeded faculty stay `PENDING`.** Otherwise the coordinator verification queue would be empty on a fresh seed and the feature couldn't be demonstrated.

## Consequences

- `RESEARCH_COORDINATOR` finally has permissions of its own (`taxonomy:manage`, `profile:verify`), so Step 2's "coordinator has an empty permission set" tests were updated rather than deleted.
- Student privacy (`is_discoverable`, default false) is stored and respected, but the only consumer — a directory that lists other people's profiles — arrives in Step 4. Step 3 has no endpoint that exposes another user's profile, so there is nothing to leak yet; Step 4 must enforce it in its queries.
- The reviewer's verification comment is stored in the audit record's `after` payload, not on `researcher_profiles` — the roadmap's schema for that table has no comment column, and the audit row already holds the rest of the decision's provenance (who, when, from what state). If a researcher ever needs to *read* why they were rejected, that needs a deliberate exposure decision, since audit logs are admin-only today.
