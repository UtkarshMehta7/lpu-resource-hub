# ADR 0003: Step 2 RBAC core decisions

- **Status:** Accepted
- **Date:** 2026-09-22
- **Context:** Step 2 adds backend-enforced RBAC per `docs/architecture.md` §6 and the Step 2 prompt in `lpu-roadmap-prompts.md`: a permission map, `require_permission`, admin user management, and an append-only audit log. No domain resources (profiles/projects/etc.) exist yet, so this step's own permission set only covers what it builds.

## Decisions

1. **Permission map derived from a role hierarchy, not duplicated per role.** `app/core/permissions.py`'s `ROLE_HIERARCHY` says `RESEARCH_COORDINATOR` inherits `FACULTY`; `ROLE_PERMISSIONS` is computed by walking that hierarchy. A later step granting `FACULTY` a permission (e.g. `project:create`) automatically extends it to `RESEARCH_COORDINATOR` with no edit to this file — matches the roadmap's explicit "COORDINATOR inherits FACULTY capabilities" requirement mechanically instead of by convention.
2. **Only enforced permissions live in code; the full design lives in `docs/rbac-matrix.md`.** Predefining permission strings for resources that don't exist yet (`project:create` before Step 5 has a `projects` table) would be exactly the kind of building-ahead-of-step the project's hard rules forbid. The matrix doc is documentation, not code — it can describe the whole system's intended shape without any of it being "built".
3. **`require_permission` wraps `get_current_user`,** so an invalid/missing token surfaces as `401` (from `get_current_user` itself, Step 1) before the permission check ever runs; a valid session lacking the permission gets `403`. Matches `docs/architecture.md` §6's status-code table exactly.
4. **Role and activation changes are separate action endpoints (`POST .../role`, `/activate`, `/deactivate`), not part of the generic `PATCH /admin/users/{id}`.** `AdminUserUpdate` (the PATCH body schema) has no `role` or `is_active` field at all — mass-assigning either is structurally impossible, not just guarded at runtime. Matches the project's "role, owner_id, status are never client-writable" hard rule and the "state transitions are explicit action sub-resources" convention (`docs/architecture.md` §8).
5. **Two policy guards, applied after the target user is loaded** (`app/modules/admin/policies.py`): no self-role-change (an admin can't change their own role through this endpoint — prevents an admin accidentally locking themselves out of admin), and no action may remove the platform's last active admin (checked for both a role change away from `ADMIN` and a deactivation). This is the "resource policy" layer from `docs/architecture.md` §6, applied to this step's own real module since no other domain resource exists yet to demonstrate it on.
6. **Deactivating a user revokes every refresh token for that user** (reusing `revoke_all_sessions`, extracted from Step 1's `change_password` into `app/modules/auth/service.py` so both call sites share it). Not strictly required for correctness — `get_current_user` and `rotate_refresh_token` both already reject an inactive user's *next* request regardless — but it's cheap, immediate, and leaves a cleaner audit trail than letting old tokens linger as unusable rows. Role changes do **not** revoke sessions: role is never trusted from the JWT (Step 1), so an old access token with a stale role claim is harmless.
7. **`coordinator_scope_id` has no foreign key.** It's a polymorphic reference — a department, school or university id depending on `coordinator_scope_type` — and none of those tables exist yet (`departments` arrives in Step 3). A single FK wouldn't even be valid for a polymorphic column regardless of table order. Validated at the application layer once the referenced tables exist.
8. **`audit_logs.actor_id` is nullable with `ON DELETE SET NULL`.** The audit trail must outlive the actor being deleted later (no user deletion exists yet, but the column shouldn't need revisiting when it does).
9. **Only role changes and activation changes are audited**, per the roadmap's explicit scope ("log role changes, activation changes"). Generic profile edits (`PATCH` full_name/coordinator_scope) are not — they're not security-sensitive in the way role/activity state is, and auditing every field edit would add noise without the roadmap asking for it.
10. **Generic `Page[T]`/`PageParams` in `app/core/pagination.py`**, used by both `GET /admin/users` and `GET /admin/audit-logs` now, intended for every future list endpoint. `page_size` capped at `MAX_PAGE_SIZE = 100` per `docs/architecture.md` §8.
11. **The authorization test matrix (`tests/test_authorization_matrix.py`) is one file that grows.** A declarative `ENDPOINTS` tuple + a role loop generates one test case per (endpoint × role-or-anonymous); a future step adds its own endpoints to that tuple rather than writing a parallel file, so the whole authorization surface stays visible in one place. 35 cases today (7 endpoints × 5 role states).
12. **Test users for roles that can't self-register** (`research_coordinator`, `admin`) are seeded directly via the ORM in tests (`tests/conftest.py`'s `seed_user` fixture) with a JWT minted directly via `create_access_token`, the same workaround `scripts/create_admin.py` uses in production.

## Consequences

- No coordinator-specific permission exists yet — `RESEARCH_COORDINATOR` has an empty effective permission set today, same as `STUDENT`. This is correct for Step 2 (no coordinator-facing resource exists) and will change the moment Step 3+ grants `FACULTY` or `RESEARCH_COORDINATOR` their first real permission.
- Admin's permissions are hand-listed, not "inherits everyone" — an admin needing to perform a coordinator-style action on a domain resource will need that permission granted to `ADMIN` explicitly when that resource's step is built, per `docs/rbac-matrix.md`'s "planned" table.
- There is still no way to create the *very first* admin except `scripts/create_admin.py` (Step 1) or direct DB access — by design; self-registration as `ADMIN`/`RESEARCH_COORDINATOR` remains rejected.
