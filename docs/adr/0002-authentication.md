# ADR 0002: Step 1 authentication decisions

- **Status:** Accepted
- **Date:** 2026-09-22
- **Context:** Step 1 adds the `users` and `auth` modules: registration, login, JWT access tokens and rotating refresh tokens, per `docs/architecture.md` §5 and `lpu-roadmap-prompts.md`'s Step 1 prompt.

## Decisions

1. **Argon2id via `argon2-cffi`, not `passlib`.** `passlib` is unmaintained; `argon2.PasswordHasher` gives Argon2id hashing/verification directly with sane defaults, no wrapper needed.
2. **PyJWT for access tokens.** HS256, signed with `JWT_SECRET_KEY` (required, minimum 32 characters, no default — the app refuses to start without one, same pattern as `DATABASE_URL`). Payload is `{sub, role, type, jti, iat, exp}` (`type="access"` distinguishes it from any future token kind; `jti` is a random id for traceability — there is no access-token revocation list, see Consequences). Every request still reloads the user from the database (`get_current_user`), so `role` and `is_active` are never trusted from the token alone.
3. **Refresh tokens are opaque and hashed at rest.** `secrets.token_urlsafe(32)` generates the raw value; only its SHA-256 hash is stored (`refresh_tokens.token_hash`). A database leak cannot be used to mint sessions.
4. **Rotation with family-based reuse detection.** Each refresh token belongs to a `family_id` (set at login/registration, carried through every rotation). Using a token marks it `revoked_at` + `replaced_by_id` and issues a new token in the same family. Presenting an already-revoked token is treated as theft/replay evidence and revokes every token in that family, forcing re-authentication everywhere that session's tokens were used.
5. **Logout revokes only the presented token**, not the whole family, so other devices/sessions are unaffected. Family-wide revocation is reserved for detected reuse.
6. **Refresh token travels only as a cookie**, `httponly`, scoped to `path=/api/v1/auth`, `secure=`(production only), `samesite` configurable via `REFRESH_COOKIE_SAMESITE` (default `lax` for same-site local dev; a cross-domain production deployment, Step 15, will need `none` + HTTPS). It is never present in a JSON response body, so it cannot be read by JavaScript or logged by an API client.
7. **Self-registration is restricted to `student` and `faculty`.** `RegisterRequest.role` is `Literal["student", "faculty"]`, not the full `UserRole` enum — matches the approved "faculty self-register" decision. `admin` and `research_coordinator` accounts are created some other way in a later step (not yet designed).
8. **No user enumeration.** Unknown email and wrong password return the identical `401` body from `/auth/login`.
9. **In-memory rate limiting on `/auth/login` and `/auth/register`, keyed by IP+email.** A fixed-window limiter (5 requests/minute per `client_ip:email` pair), consistent with the architecture's "no Redis, in-memory, behind an interface" rule. Keying by IP+email (not IP alone) means one abusive IP can't lock every account behind it out of the rate limit, and — combined with each IP having its own budget — a distributed attempt against one email still costs an attacker many source IPs. The limiter instance lives on `app.state` (set in `create_app()`, alongside `settings`), not as an import-time global, so each app instance — including test apps — has independent counters.
10. **CORS credentials enabled.** `allow_credentials=True` now that the refresh cookie exists (ADR 0001 flagged this as deferred to Step 1).
11. **Model registry for Alembic.** `app/db/model_registry.py` imports every ORM model; `alembic/env.py` imports that one module instead of individual model modules, so adding a module's models to the registry is the only step future migrations need.
12. **Tests migrate a real database.** `db`-marked tests run `alembic upgrade head` against `TEST_DATABASE_URL` (session-scoped fixture) instead of `Base.metadata.create_all()`, which the project's conventions forbid — this actually proves the migration, not just the ORM models.
13. **Password policy: minimum 10 characters plus a small common-password blocklist** (`app/core/security.py: MIN_PASSWORD_LENGTH`, `COMMON_PASSWORDS`), enforced in both `RegisterRequest` and `ChangePasswordRequest`. Not a substitute for a breach-corpus check (e.g. k-anonymity against Have I Been Pwned), which needs an external call and is out of scope for a local-only, zero-cost prototype — this just closes the obvious gap where a 10-character minimum alone would still accept `"password123"`.
14. **CSRF defence on `/auth/refresh` and `/auth/logout`: require a non-empty `X-Requested-With` header.** These two endpoints are reachable with just an ambient cookie (no bearer token), which is exactly the shape of request a CSRF attack forges. A cross-site HTML form cannot set custom headers, but our own same-origin frontend JavaScript can — the axios client sends it on every request. This is defence in depth on top of `SameSite=Lax`, not a replacement for it.
15. **`GET /api/v1/me`, not `/api/v1/users/me`.** Matches the roadmap's exact endpoint contract. The `users` module still owns the handler (`app/modules/users/router.py`) — it's just mounted with no extra path segment.
16. **`POST /api/v1/auth/change-password`** verifies `current_password`, then re-hashes and revokes every refresh token for that user (all sessions/devices signed out), consistent with the "logout only revokes the presented token" rule in decision 5 — a password change is exactly the case where every *other* session should also end.
17. **`backend/scripts/create_admin.py`.** `admin` and `research_coordinator` cannot self-register (decision 7), so this is the only way to create one: an interactive CLI that prompts for email/name/role/password (via `getpass`, confirmed twice) and writes the user directly. Never accepts a password as a CLI argument or environment variable. `backend/scripts/` was deliberately empty until now (ADR 0001, item 12) — this is its first content.

## Deviations from the roadmap prompt

- **No `openapi-typescript` codegen for the frontend.** The frontend's `features/auth/types.ts` is hand-written to mirror the backend's Pydantic schemas field-for-field (same approach `features/system-status/api.ts` already used for `ReadinessResponse` in Step 0). For a two-schema surface (`UserRead`, `AccessTokenResponse`) this gives the same type safety as generated types with less moving infrastructure (no build-time dependency on a running backend, no generated-file drift to review). Revisit this once the API surface is large enough that hand-syncing becomes error-prone — likely by Step 4 or 5.

## Consequences

- Access tokens are stateless and short-lived (15 min default); revocation only affects the ability to get a *new* one via refresh, not an already-issued access token. Acceptable for a 15-minute window at prototype scale; a token-revocation/blocklist for access tokens is not implemented (the `jti` claim exists for future use, e.g. audit logging, but nothing checks it today).
- `role` and `research_coordinator` scoping, permission checks and query-level authorization are still Step 2 — `GET /me` requires only a valid, active session, not any particular role.
- There is no way yet to deactivate a user or change a user's role after creation (both are Step 2, admin-user-management territory); `create_admin.py` and direct DB access are the only levers today.
