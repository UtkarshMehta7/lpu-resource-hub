1. Problem, goal and scope

1.1 The problem

Inside a large university, research capability is invisible across departmental boundaries. Faculty expertise, ongoing projects and available laboratory equipment are known locally and almost nowhere else. Three costs follow directly:

  • Collaborators never meet. Two researchers working on adjacent problems in different schools have no mechanism to discover one another.
  • Students cannot find research. Opportunities circulate by word of mouth, so access depends on who a student already knows.
  • Resources idle and deadlines pass. Equipment goes under-used because nobody outside the owning department knows it exists; funding calls are missed for want of a reminder.

1.2 The goal

One platform where research capability is discoverable, collaboration is initiated and continued in the open, shared facilities are bookable, and funding deadlines announce themselves — with every action governed by university hierarchy rather than by a free-for-all.

1.3 Scope and constraints

ConstraintConsequence for the design
Zero costNo paid APIs, no mandatory cloud services. Machine learning runs locally (scikit-learn, sentence-transformers). Docker is optional.
PostgreSQL onlyFull-text search, trigram fuzzy matching, exclusion constraints and vector similarity are all done in the database; no Elasticsearch, no vector service.
No message brokerIn-memory rate limiting, an in-process scheduler and synchronous domain events — each behind an interface so it can be replaced.
Fictional data onlyThe platform is a prototype. It must never present fabricated records as real university data, and says so on every page.

2. System architecture

2.1 Why a modular monolith

Microservices would multiply deployment cost and operational surface for a project that must run at zero cost on one instance. The seams that matter — router / service / policy / repository, and a pluggable recommendation strategy — are enforced inside one deployable, so the ML layer or any module can be extracted later without re-architecting.

4. Data model and entity relationships

4.1 Database conventions

  • UUID primary keys via gen_random_uuid(); created_at / updated_at as timestamptz.
  • PostgreSQL enums for workflow statuses; CHECK constraints for invariants that must never be violated.
  • Every schema change is a reviewed Alembic migration with a sequential id. create_all() is never used.
  • Deterministic constraint naming, so migrations are readable and reversible.

4.2 Constraints that carry real rules

ConstraintWhat it makes impossible
UNIQUE(user_a_id, user_b_id) with CHECK (user_a_id < user_b_id)Two people having more than one collaboration relationship, in either direction. Duplicates are impossible in the database rather than guarded in code.
EXCLUDE USING gist on bookingsTwo approved bookings overlapping on the same equipment. The database refuses; no application race can produce a double-booking.
Partial UNIQUE on notifications dedupe_keyThe same reminder being sent twice, however often the scheduler runs.
CHECK exactly-one-of on conversations and tag aliasesA thread belonging to both a collaboration and a project, or to neither.
UNIQUE on registration_number, case-normalisedTwo accounts sharing a university identity.

5. Roles, permissions and account provisioning

5.1 Account provisioning

There is no public registration. POST /auth/register does not exist, and a test asserts the OpenAPI document contains no such path. Accounts descend the institutional hierarchy: an administrator appoints research coordinators, a coordinator provisions the faculty of the department they oversee, and a faculty member enrols their own students.

The new account's role is derived from the creator and never read from the request body — there is no client-supplied role to forge. Each new user receives a temporary password they must replace before they can use anything else.

5.2 Administrator handover

Promoting somebody to administrator requires two people. A six-digit code is generated, hashed with SHA-256, and delivered to the target's notification inbox — not the requester's. It expires in ten minutes, is single-use, and allows five attempts. Administration also has its own sign-in page, and the server refuses the wrong entrance for each role. That check runs after the password is verified, so the administration page can never become an oracle telling an attacker which registration numbers belong to administrators.

6. Feature catalogue

6.1 Identity and onboarding

  • Sign in with the LPU registration number (UMS-style); email is optional contact information, never a credential.
  • Two separate entrances — administration and the main platform — enforced server-side.
  • Forced password replacement on first sign-in; the application is locked until it is done.
  • Onboarding wizard — profile basics, skills, research areas — with a stored completeness flag.
  • Role-aware profiles: students declare programme, year and discoverability; researchers declare designation, availability and links.

6.2 Discovery

  • Researcher directory with full-text and typo-tolerant (trigram) search, filtered by department, research area, skill and availability.
  • Search by registration number — matched as a case-insensitive prefix, not through the language analyser, because an identifier is not prose.
  • Opt-in student discovery. Students are invisible to search unless they choose otherwise; only public profile fields are ever exposed.
  • Unified search across researchers, projects, publications and opportunities.
  • Natural-language search — sentence embeddings in pgvector fused with full-text ranking; degrades cleanly to lexical search when the optional model is not installed.
  • Command palette (⌘K / Ctrl+K) reaching all 28 destinations, offering only pages the signed-in role may open.

6.3 Research work

  • Projects with a reviewed lifecycle, team members, research areas, skills and visibility rules.
  • Publications with ordered internal and external author lists, DOI de-duplication and project links.
  • Opportunity board — research assistant, thesis, internship and collaboration openings, with positions and deadlines.
  • Applications with a status timeline, applicant review and automatic addition to the project team on acceptance.

6.4 Connection

  • Collaboration relationships — one per pair of people, in either direction, with a request/accept/decline/cancel/end lifecycle.
  • Conversation threads scoped to an accepted collaboration or a project team. There is no open inbox and no endpoint that creates a thread: threads appear as a consequence of agreement.
  • One thread per pair for its life — collaborating again reopens the same conversation instead of splitting two people's history.
  • Notifications from domain events, with deduplication: twenty messages produce one notice until it is read.
  • Deadline reminders at seven days and one day, from an in-process scheduler.

6.5 Resources

  • Facility and equipment catalogue with a week calendar.
  • Booking requests and approvals, with double-booking prevented by a database exclusion constraint rather than by application logic.
  • Funding calls (fictional) that can be saved, with deadline reminders.

6.6 Governance

  • Faculty verification queue — department-scoped for coordinators, platform-wide for administrators; nobody may verify their own profile.
  • Project review queue; a reviewer may never approve their own project.
  • Content reports and moderation, able to hide content without destroying it.
  • Append-only audit log for every sensitive action, readable by administrators.
  • Scoped analytics — coordinators see their department, administrators the platform — plus a collaboration network graph.
  • Account deletion down the hierarchy, with the cascade counted and shown before anything is destroyed.

8. Security model

ControlImplementation
Password storageArgon2id with per-password salt. Passwords are never logged, returned or comparable in plaintext.
Session15-minute JWT access token held in memory only — never in localStorage, so an XSS cannot read it at rest.
RefreshOpaque 7-day token in an httpOnly; Secure; SameSite cookie scoped to /api/v1/auth, stored as a SHA-256 hash, rotated on every use. Reuse of a retired token revokes the entire family.
CSRFEvery browser request carries X-Requested-With; the cookie is same-origin via the Netlify proxy.
AuthorizationThree server-side layers (§5). Role and active status re-read from the database on every request.
Information disclosure404 — not 403 — wherever a user must not learn a resource exists: another department's queue, a conversation they are not in, an administrator's registration number.
Rate limitingPer-user and per-IP budgets on sign-in, search, collaboration requests and messages.
Transport and headersHSTS, CSP, X-Content-Type-Options, frame denial. API docs disabled in production.
SecretsNever committed. All configuration via environment variables; .env.example holds placeholders only. CI runs a secret scan and dependency audit on every push.
AuditAppend-only log of every sensitive action — role changes, approvals, deletions, administrative overrides — recording actor, entity, before/after and IP.

9. AI and recommendation engine

Recommendations are explainable by design. Every suggestion carries the reasons it was made, because a black box that cannot justify itself will not be trusted by the researchers it is advising.

SignalMethodWeight
Skill overlapSet intersection against the viewer's declared skillsHighest
Research-area overlapTaxonomy match, including two-level parent relationshipsHigh
Textual similarityTF-IDF vectors with cosine similarity (scikit-learn), computed locallyMedium
Semantic similaritySentence-transformer embeddings in pgvector, fused with full-text rankOptional
Recency and availabilityOpen positions, deadlines, stated availabilityTie-break

A user with a sparse profile receives a cold-start response that says so plainly and offers the newest relevant items rather than pretending to a confidence it does not have. The engine is a pluggable strategy, and an offline evaluation script measures ranking quality.

A principle learned the hard way: passing tests are not a working screen. A one-time administrator code was delivered correctly and rendered invisibly, with every test green, because a display function had no case for it. New interface work is therefore driven in a real browser before it is called done.

11. Deployment architecture

11.1 Release process

A push to main deploys. The API applies outstanding Alembic migrations at startup and, if that fails, starts degraded and reports the reason on /health/ready rather than refusing to serve — a failed deploy leaves the previous image running and the fault invisible. Data-rewriting migrations are still run deliberately from a workstation before the code that needs them merges.

12. Design decisions (ADR index)

Twenty-four architecture decision records in docs/adr/. The most consequential:

ADRDecisionWhy it mattered

0017Deployment and hardeningFree-tier topology, security headers, cookie strategy.
0018Department membershipSelf-declared until verification locks it; an administrator can always correct it.
0019Provisioning hierarchyRemoved public registration; the role is derived from the creator, never sent by a client.
0020Identity on screen, derived coordinator scopeThe UID appears wherever a person is named; a coordinator's scope follows their department automatically, because one with no scope silently oversaw nothing.

0024Migrate at startupCode repeatedly reached production ahead of its migration. The instance now heals itself and reports failure honestly.

13. Known limitations and future work

LimitationReasoning and the path forward
Messaging polls rather than pushesDeliberate: synchronous SQLAlchemy, no Redis, and a free instance that sleeps. A 10-second poll that pauses when the tab is hidden is indistinguishable from real time at this scale. Server-Sent Events are the upgrade path — one endpoint, no schema change.
Semantic search optional in productionThe sentence-transformer model exceeds a free instance's memory. Embeddings can be precomputed offline, or the paid tier used.
Single application instanceRate limiting and the scheduler are in-process. Horizontal scaling needs shared state — both already sit behind interfaces.
Notifications are in-app onlyEmail or push would need a provider and therefore a cost.
All data is fictionalIntegration with real university systems is deliberately out of scope for a prototype.
